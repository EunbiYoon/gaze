4. Next: training-length diagnosis (judged on train fold only)

Train success was still rising at iter 400. Check whether more iters push train success above greedy level (≈60%). Decide only from train succ in the log — do not pick iters by looking at held-out results.

# Inside a 1-GPU allocation (e.g. in tmux after salloc)
CUDA_VISIBLE_DEVICES=0 python -m waldo_gaze.run --config configs/coco_search18.yaml \
  --specs clip_full --folds 0 --seeds 0 \
  --set ppo.iters=1500 results_dir=results/coco_search18_diag_iters \
  > logs/coco_search18/diag_iters.log 2>&1

grep -E "it +(0|300|600|900|1200|1490) " logs/coco_search18/diag_iters.log
  • A separate results_dir is required; a run is skipped if a run json with the same name exists.
  • 400 iters took about 77 s, so 1500 iters is roughly 5 minutes.
If train succ exceeds 60% → fix that iters value (chosen on train), rerun 3 specs × 2 folds, and compare against greedy at the same budget.
If it stays at ≈50% even at 1500 iters → training length is not the problem. Look first at the policy inputs and action structure (zoom cost, stop decision) or the reward structure.

Principles

  • Hyperparameters and prompts are never changed after looking at test results. Only κ is selected, on the train fold.
  • Change code with patches. Do not overwrite with unzip -o (it once reverted activate.sh to the waldo env).
  • Runs inside tmux keep going after the terminal closes. Detach with Ctrl-b d, reattach with tmux attach -t m5.
